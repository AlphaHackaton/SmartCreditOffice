# client-credit-application Specification

## Purpose

Дать предпринимателю проверяемый путь подачи кредитной заявки и получения одобренного финансирования с объяснением решения и подписанием внутри веб-интерфейса.

## Requirements

### Requirement: Данные компании и заявки

Кабинет SHALL показывать подтверждённый API профиль текущей компании и её заявки с явными состояниями загрузки, отсутствия данных и ошибки. При недоступности данных SHALL не подставляться синтетические показатели.

#### Scenario: Вход Соколовой
- **WHEN** клиент Соколова успешно входит и API возвращает её компанию и заявки
- **THEN** кабинет показывает эти данные и переход к новой заявке без повторного ручного ввода профиля

### Requirement: Оформление финансирования

Форма SHALL использовать продукты и ограничения API, принимать сумму, срок, цель и необходимые согласия, показывать ошибки полей и передавать деньги строками. Отправка SHALL блокироваться при некорректном вводе, отсутствии обязательного согласия и выполняющемся запросе.

#### Scenario: Обязательные согласия не приняты
- **WHEN** клиент пытается отправить форму без обязательного согласия
- **THEN** видит объяснение, а запрос подачи не отправляется

#### Scenario: Однократная подача
- **WHEN** клиент отправляет корректную заявку и повторно нажимает кнопку во время запроса
- **THEN** выполняется одна команда, после ответа открывается созданная заявка, а кнопка возвращается в доступное состояние при ошибке

### Requirement: Статусы и история с сервера

Страница заявки SHALL отображать серверный статус и историю переходов с московским временем. Ожидающие состояния SHALL обновляться автоматически без фиктивных процентов и локального присвоения решения; уход со страницы или завершение процесса SHALL прекращать её опрос.

#### Scenario: Скоринг после отправки
- **WHEN** API возвращает SUBMITTED либо SCORING
- **THEN** клиент видит ожидание проверки, а последующие чтения получают действующий статус и историю

#### Scenario: Завершение процесса
- **WHEN** API возвращает DISBURSED
- **THEN** показывается «Кредит выдан», а дальнейший автоматический опрос этой заявки прекращается

### Requirement: Прозрачное одобрение

При APPROVED интерфейс SHALL показывать актуальные офферы, их срок действия, условия и клиентские объяснения API. Финансовые показатели SHALL отображаться без самостоятельного расчёта ставки, платежа и решения. Только актуальный доступный оффер SHALL позволять перейти к подписанию.

#### Scenario: Клиент изучает одобрение
- **WHEN** API возвращает одобренные условия и клиентские факторы
- **THEN** клиент видит сумму, срок, ставку, платёж и причины ровно из ответа, без служебной трассы банка

#### Scenario: Истёкший оффер
- **WHEN** срок действия оффера истёк либо сервер отклоняет его принятие как истёкшее
- **THEN** подписание не начинается, интерфейс обновляет заявку и сообщает о недоступности условий

### Requirement: Подпись и выдача внутри UI

После принятия оффера интерфейс SHALL использовать выданное API подтверждение и показывать код только внутри кабинета. Успешный запрос подписи SHALL не считаться выдачей до получения DISBURSED. Внешние сообщения и реальные платёжные операции SHALL отсутствовать.

#### Scenario: Положительный сквозной путь
- **WHEN** Соколова принимает актуальный оффер, подтверждает подпись внутри UI, а локальный API переводит заявку в DISBURSED
- **THEN** интерфейс показывает подтверждённую выдачу и историю без SMS, email и локальной подмены статуса

#### Scenario: Неверный код
- **WHEN** API отклоняет код подтверждения
- **THEN** показывается ошибка и возможность исправления без сообщения об успешной подписи или выдаче

#### Scenario: Подписано, но ещё не выдано
- **WHEN** сервер возвращает SIGNED
- **THEN** интерфейс показывает ожидание выдачи и продолжает чтение до следующего серверного статуса

### Requirement: Другие исходы и ограничения действий

Для COUNTER_OFFER, REJECTED, UNDERWRITING, CANCELLED и EXPIRED интерфейс SHALL показывать соответствующий смысл и доступные клиентские причины, скрывая действия, не разрешённые этим этапом. Полноценный симулятор и ручное решение сотрудника SHALL не имитироваться.

#### Scenario: Отказ
- **WHEN** сервер возвращает REJECTED с клиентским объяснением
- **THEN** клиент видит отказ и причины без кнопки подписи

#### Scenario: Контроффер
- **WHEN** сервер возвращает COUNTER_OFFER
- **THEN** интерфейс сообщает о встречном предложении и показывает данные API без недействующего симулятора или команды подписи из одобренного пути

#### Scenario: Ручное рассмотрение
- **WHEN** сервер возвращает UNDERWRITING
- **THEN** клиент видит ожидание сотрудника, без самостоятельного принятия решения

### Requirement: Ошибки и конфликты

Сетевая ошибка, отсутствие доступа, недоступная заявка и конфликт версии SHALL отображаться явно. Команда с конфликтом SHALL не повторяться автоматически: интерфейс SHALL перечитать заявку и предложить действие на актуальных данных. Поля с ошибками API SHALL сохранять пользовательский ввод.

#### Scenario: Конфликт принятия оффера
- **WHEN** API возвращает 409 при принятии оффера
- **THEN** интерфейс показывает конфликт, перечитывает заявку и не повторяет команду самостоятельно

#### Scenario: Чужая заявка
- **WHEN** API возвращает 403 либо 404 при прямом открытии заявки
- **THEN** интерфейс показывает недоступность и переход в кабинет без отображения чужих данных

### Requirement: Воспроизводимая проверка

Завершение положительного сценария SHALL проверяться против локального stub API с детерминированными синтетическими данными Dev 2. Компонентные фикстуры SHALL соответствовать сгенерированной схеме. При отсутствии backend интеграционный этап SHALL оставаться невыполненным.

#### Scenario: Контракт ещё не опубликован
- **WHEN** OpenAPI или работающий stub отсутствуют
- **THEN** интеграционные задачи не отмечаются выполненными и успешная выдача не заменяется демонстрационной анимацией
