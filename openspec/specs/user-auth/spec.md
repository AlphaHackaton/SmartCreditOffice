# user-auth Specification

## Purpose

Обеспечить вход предпринимателя и сотрудника в единый кабинет с подтверждённой сервером ролью, понятной терминологией и изоляцией сессий и рабочих пространств.

## Requirements

### Requirement: Названия рабочего пространства сотрудника

Интерфейс SHALL использовать «Сотрудник банка» для обозначения пользователя, «Вход для сотрудников» для соответствующей точки входа и «Рабочее место кредитного специалиста» в служебном контуре. Технические пути `/bank/*` SHALL сохраняться.

#### Scenario: Открытие служебного контура
- **WHEN** сотрудник открывает своё рабочее пространство
- **THEN** видит «Рабочее место кредитного специалиста», а адрес остаётся в `/bank/*`

### Requirement: Вход по подтверждённой роли

Вход SHALL выполняться через API с тестовыми учётными данными внутри UI. Рабочее пространство SHALL определяться подтверждённой сервером ролью. Выбор подписи или точки входа SHALL не предоставлять права сотрудника.

#### Scenario: Вход сотрудника
- **WHEN** API успешно проверяет учётные данные и подтверждает роль сотрудника
- **THEN** открывается очередь заявок сотрудника без ручного переключения роли

#### Scenario: Ошибка входа
- **WHEN** API отклоняет учётные данные
- **THEN** форма сохраняет введённый логин, показывает понятную ошибку и не открывает защищённые данные

#### Scenario: Выбор входа для сотрудников клиентом
- **WHEN** предприниматель вводит действующие клиентские данные через точку «Вход для сотрудников»
- **THEN** его права остаются клиентскими и интерфейс не открывает служебные данные

### Requirement: Защищённая навигация

До подтверждения пользователя интерфейс SHALL не показывать и не запрашивать бизнес-данные защищённого контура. Неавторизованный посетитель SHALL направляться на вход; посетитель с иной ролью SHALL получать понятное сообщение о недоступности раздела.

#### Scenario: Прямой адрес без входа
- **WHEN** посетитель без сессии открывает адрес заявки
- **THEN** видит вход, а данные заявки не запрашиваются

#### Scenario: Клиент открывает служебный адрес
- **WHEN** авторизованный клиент открывает `/bank/applications`
- **THEN** видит отказ в доступе и ссылку в свой кабинет без запроса служебной очереди

#### Scenario: Определение текущего пользователя
- **WHEN** токен получен, но API ещё не подтвердил текущего пользователя
- **THEN** показывается состояние ожидания без содержимого клиентских или служебных страниц

### Requirement: Выход и изоляция сессии

Выход и истечение сессии SHALL удалять токен и данные пользователя, отменять запросы, очищать кеш и возвращать на вход. Запоздалый ответ предыдущей сессии SHALL не восстанавливать её данные и не завершать новую сессию. Перезагрузка SHALL требовать повторного входа при хранении токена только в памяти.

#### Scenario: Выход и вход другого пользователя
- **WHEN** один пользователь выходит, а другой входит в тот же браузер
- **THEN** данные первого не отображаются и не используются в запросах второго

#### Scenario: Перезагрузка страницы
- **WHEN** пользователь обновляет страницу при хранении токена в памяти
- **THEN** интерфейс возвращается на вход без восстановления фиктивной авторизации

### Requirement: Доступность API и демо-учёток

Демо-персоны SHALL поступать из локального API, без собственной копии seed-данных во frontend. При недоступности API интерфейс SHALL показывать ошибку соединения и возможность повтора без имитации успешного входа. Пароли и токены SHALL не попадать в логи и постоянное хранилище браузера.

#### Scenario: Сервер недоступен
- **WHEN** запрос входа не может связаться с API
- **THEN** форма остаётся доступной, показывает ошибку соединения и не создаёт сессию

#### Scenario: Демо-персоны загружены
- **WHEN** API возвращает список доступных тестовых пользователей
- **THEN** интерфейс использует этот список без локального дублирования компаний и ожидаемых решений
