# Design

## Context

Мотивация — в proposal.md. В frontend уже есть Alfa-компоненты, strict TypeScript, Vitest и Testing Library; shared/format.ts отсутствует. В ARCHITECTURE:638 заданы formatMoney, formatPct и московские даты, но API ещё не опубликован. Существующая задача frontend-client-flow/3.1 также включает generated-статусы и Timeline, поэтому полностью закрыть её сейчас нельзя.

Это отдельное изменение только для отображения значений. Оно не меняет зависимость этапов B/C клиентского пути от API и не вводит собственного доменного контракта. Остаёмся в текущей ветке; прежние коммиты и пользовательские изменения не затрагиваются.

## Goals / Non-Goals

**Goals:** точные строки сумм/процентов, отдельная обработка календарных дат и событий, повторно используемые компоненты с понятным отсутствием значения.

**Non-Goals:** расчёт условий кредита, нормализация ввода заявки, статусы и таймлайн, API/БД, отображение тестовых показателей в реальном кабинете.

## Decisions

### 1. Строковые суммы и проценты

В shared/format.ts экспортируются formatMoney(value), formatPct(value), formatDate(value) и formatDateTime(value), принимающие string/null/undefined и возвращающие string. Защита runtime проверяет тип и синтаксис даже при нарушенном входном TS-контракте; недоступное значение — `—`.

Для денег допускается десятичная строка с необязательным минусом, хотя бы одной целой цифрой и 0–2 дробными знаками. Пробелы, запятая на входе, плюс, экспоненциальная запись и лишняя точность не принимаются. Ведущие целые нули убираются; копейки дополняются до двух; разряды группируются U+00A0, затем запятая, копейки и U+00A0 перед ₽. Отрицательный ноль отображается как обычный ноль. Цифры обрабатываются только строковыми операциями.

formatPct использует аналогичный разбор, но допускает произвольное число дробных цифр. Удаляются только конечные дробные нули; значение не умножается на 100. Разделитель — запятая, перед % — U+00A0. Нет собственных диапазонов ставок: за условия отвечает backend.

Альтернатива Number/parseFloat + Intl.NumberFormat для денег отклонена: она теряет цифры больших значений и может округлить данные. Decimal-библиотека не нужна для отображения без вычислений.

### 2. Даты и часовой пояс

formatDate принимает строго YYYY-MM-DD (годы 0001–9999), проверяет реальный календарный день, включая високосный год, и возвращает DD.MM.YYYY строковыми частями. Дата регистрации не является моментом времени и не переводится между часовыми поясами.

formatDateTime принимает полную ISO-метку YYYY-MM-DDTHH:mm:ss с необязательными долями секунды и обязательным Z либо смещением ±HH:mm. Проверяются календарные части, часы/минуты/секунды и offset. Невозможные даты не должны нормализоваться автоматически в следующий месяц. Метки без timezone и произвольные локальные строки отклоняются. Для валидной метки используется Date и Intl.DateTimeFormat с ru-RU, timeZone=Europe/Moscow и 24-часовым временем; результат фиксируется как DD.MM.YYYY, HH:mm. Перевод даты допускает переход дня/месяца/года.

Альтернатива — default timezone устройства — отвергнута: разные устройства иначе показали бы историю заявки. Date-библиотеку не добавляем: стандартных API достаточно. Запрет денежного Number не относится к стандартной работе Date со временем.

### 3. Компоненты

MoneyText(value) использует formatMoney и табличные цифры для будущих таблиц/офферов. DateTimeText(value, kind) использует formatDate при kind=date и formatDateTime при kind=timestamp (по умолчанию). Для корректной даты рендерится семантический time с исходным dateTime. Для некорректной/отсутствующей — обычный текстовый элемент без ложного dateTime.

При недоступности виден `—`; скрытый доступный текст сообщает «Сумма недоступна» или «Дата недоступна». Реализовать это текстом, доступным screen reader, а не только title или aria-label на несемантическом span. Компоненты не изменяют значение, не обращаются к сети и не подставляют тестовые суммы в страницы-заглушки.

### 4. API, данные и дальнейшее подключение

Новые endpoint, wire-схемы, DTO и модели БД: отсутствуют. Форматтеры работают с примитивными значениями, поэтому не требуют OpenAPI, роли, копии personas или перечислений статусов. Они подготавливают часть frontend-client-flow/3.1; при её реализации переиспользуются, а задача остаётся открытой до статусов/Timeline и generated-типов. Существующие артефакты клиентского пути не изменяются в этом propose.

Новых зависимостей нет; package.json/lock и сведения о лицензиях менять не требуется, если apply не выявит обоснованную необходимость. Правила скоринга, факторы, веса и пороги не меняются.

### 5. Проверки

Unit-тесты: большие суммы за пределами Number.MAX_SAFE_INTEGER, отрицательные значения/ноль/ведущие нули, 0–2 копейки и отказ округления, точные Unicode-разделители; целые/дробные проценты с сохранением значащих цифр; пустые и некорректные значения без исключений. Календарь: високосные годы, невозможные дни, формат даты; события: Z и offset, переход дня/года, отсутствие timezone, недопустимые поля.

Компонентные проверки: видимый текст, доступное описание недоступности, time/dateTime только для корректной даты. Проверить время в окружениях TZ=UTC и TZ=Asia/Tokyo, чтобы подтвердить независимость результата от устройства. Тестовые строки локальные и не являются реальными данными компаний. Все проверки выполняются без backend.

## Risks / Trade-offs

- [Будущий API вернёт деньги с лишней точностью] → Показать недоступность вместо молчаливого округления; согласовать формат с Dev 2 при подключении.
- [Date автоматически нормализует неверный день] → Проверять календарные поля до отображения, не полагаться только на Date.parse.
- [Статусы и DTO ещё отсутствуют] → Не закрывать frontend-client-flow/3.1 и не создавать ручные enum; здесь только отображение примитивов.
- [Новые компоненты пока не используются в реальных экранах] → Проверить их изолированно; подключение — при реализации кабинета и офферов после API.

## Migration Plan

При apply добавляются только shared-форматтеры/компоненты, тесты и README. Миграций и замены данных нет. Откат — revert отдельного frontend-коммита. Полное закрытие требует build, тестов, OpenSpec strict и harness exit 0; синхронизация specs — через archive после реализации.
