# Design

## Context

Мотивация и границы описаны в `proposal.md`. Изучены `AGENTS.md`, план Dev 3 (`docs/ARCHITECTURE.md:621–690`), план API (`:580–593`) и риски интеграции (`:754–772`). На момент подготовки нет `frontend/`, `backend/app/main.py`, `docs/openapi.json` и основных OpenSpec-спецификаций. Есть доменные перечисления и FSM в backend, но это не опубликованный HTTP-контракт.

Рабочая ветка — `codex/frontend-shell`. Незакоммиченные изменения среды из предыдущей работы сохраняются; они не являются реализацией этого предложения.

## Goals / Non-Goals

**Goals:**
- Получить отдельно запускаемый frontend с готовыми провайдерами, адресами разделов и проверяемым API-транспортом.
- Устранить зависимость запуска каркаса от готовности API Dev 2.
- Оставить точки расширения для следующих клиентских и банковских экранов без дублирования финансового домена.

**Non-Goals:**
- Авторизация по учётным данным, проверка прав на сервере и действующие бизнес-операции не реализуются; здесь только инфраструктура сброса сессии.
- Правила скоринга, таблицы факторов, веса и пороги не меняются: они вне этого frontend-изменения.
- Готовая поставка через nginx/Compose не входит в каркас. Dockerfile и production history fallback добавляются вместе с интеграцией Dev 2.

## Decisions

### 1. Зависимости и проверяемая сборка

React и React DOM фиксируются на совместимых версиях 18.x. Vite с React-плагином, TypeScript strict, Alfa Core Components, TanStack Query и react-router следуют заданному стеку. Конкретные совместимые версии фиксируются lock-файлом при apply; перед установкой проверяются peerDependencies, документация импорта компонентов и CSS Alfa. Применять `--force`/`--legacy-peer-deps` для обхода несовместимости нельзя.

Dev-инструменты: ESLint с конфигурацией TypeScript/React, Vitest, jsdom, Testing Library и openapi-typescript. Один `tsconfig.json` с `include: ["src", "vite.config.ts"]`, без project references; eslint игнорирует `dist` и генерируемый `src/api/schema.d.ts`. Скрипты: `dev`, `build`, `preview`, `lint`, `typecheck`, `test`, `gen:api`. `build` включает проверку типов и Vite-сборку. Установка воспроизводится через `npm ci`.

Альтернатива — неизменённый шаблон Vite с references — не подходит: существующий harness вызывает `tsc --noEmit -p .`. Новые зависимости сразу отражаются в `package-lock.json` и `THIRD_PARTY_NOTICES.md`.

### 2. Структура и провайдеры

```text
frontend/
  package.json, package-lock.json, tsconfig.json, vite.config.ts, eslint.config.js
  index.html, README.md, scripts/gen-api.mjs
  src/
    main.tsx, App.tsx, router.tsx
    api/client.ts, errors.ts, query-client.ts
    auth/session.tsx
    shared/components/AppLayout.tsx, PlaceholderPage.tsx, NotFoundPage.tsx
    shared/styles.css
    test/setup.ts
```

`main.tsx` подключает React root и стили; корневые провайдеры создают стабильный QueryClient и сессию, router использует их общий контекст. Сессию храним только в памяти; токены не пишутся в localStorage и не выводятся в лог. API-обёртка принимает функции чтения текущего токена и уведомления о 401. Тест может установить синтетическую сессию через этот контракт без добавления фальшивой формы входа в приложение.

Альтернатива — поместить API-запросы и состояние сессии в страницы — привела бы к расхождению обработки ошибок. Бизнес-хуки `queries.ts`, ключи заявок, форматтер денег и карта статусов добавятся при наличии настоящих DTO, без ручного копирования enum из Python.

### 3. Маршруты и общий layout

| Адрес | Содержимое в этом изменении |
|---|---|
| `/` | Redirect с replace на `/client` |
| `/login` | Заглушка входа; форма и вход не имитируются |
| `/client` | Заглушка кабинета клиента |
| `/client/applications/new` | Заглушка новой заявки |
| `/client/applications/:id` | Заглушка заявки с идентификатором |
| `/bank/applications` | Заглушка очереди |
| `/bank/applications/:id` | Заглушка досье с идентификатором |
| `/bank/metrics` | Заглушка метрик |
| `*` | Страница 404 и ссылка на `/client` |

`AppLayout` содержит шапку, боковую навигацию и основную область. Контур определяется маршрутом; ссылки «Клиент» и «Банк» переключают только предварительный просмотр. Видимая пометка объясняет отсутствие авторизации и данных. Это не переключатель ролей действующего пользователя. Клиентские/банковские запросы в заглушках отсутствуют, поэтому открытый предварительный просмотр не раскрывает данные. Настоящий `RequireRole` будет введён вместе с входом и server-side RBAC.

Alfa-компоненты используются для видимых элементов каркаса с официальными стилями и импортами по компонентам. Desktop-layout проверяется при ширинах 1280 и 1440; адаптивные breakpoint и мобильное меню не добавляются. Разметка использует header/nav/main, ссылки с aria-current и видимый focus. Для тестов маршруты доступны через memory-router; браузерная сборка использует history-router.

### 4. API-транспорт и ошибки

`api/client.ts` предоставляет транспорт с базой `/api/v1`, сериализацией JSON и AbortSignal. Допускаются только относительные пути внутри этого префикса: внешние/protocol-relative адреса и выход через `..` отклоняются до fetch. Токен берётся перед запросом; Authorization отсутствует без сессии. Денежные строки не преобразуются в number. Прокси Vite перенаправляет `/api` на `http://localhost:8000`, браузер обращается к своему origin.

Успех: JSON разбирается как `unknown`, 204 возвращает `undefined`; типизированный generic не считается runtime-валидацией DTO. Ошибка `ApiError` хранит HTTP-статус либо null для сетевой ошибки, код, безопасное сообщение и необязательные details типа unknown. Входящее тело проверяется структурно: формат `{code, message, details}` — ожидаемый архитектурный формат, пока не объявляем его сгенерированным ErrorDTO. Для HTML/пустых/повреждённых ошибок есть резервные тексты; ошибка разбора успешного JSON получает отдельный код протокола. AbortError сохраняется как отмена.

QueryClient отключает автоматические retry на этапе каркаса; повторный вход и автоматический refetch после 409 реализуются в будущих бизнес-хуках. При 401 текущей сессии обработчик удаляет токен, отменяет запросы, очищает QueryClient и направляет на `/login`. 401 от запроса старой сессии не должен стирать новую: обработчик сверяет захваченный токен с текущим. Для 403/409/422 сброса нет. Повторного выполнения команд нет.

Альтернатива — отдельные HTTP-клиенты для банка и клиента — избыточна: база и формат ошибок общие; разграничение доступа обеспечивает будущий backend, а не URL страницы.

### 5. Граница OpenAPI и backend

Новые endpoint, DTO и модели БД: **отсутствуют**. Архитектурные пути `/auth/login`, `/auth/me`, `/products`, `/applications` и `/bank/applications` — ориентир следующих изменений, не HTTP-контракт этого каркаса.

`npm run gen:api` читает исключительно `../docs/openapi.json` и генерирует `src/api/schema.d.ts`. До публикации схемы команда сообщает «Нужен docs/openapi.json от Dev 2» и завершается ненулевым кодом. Сборка, типизация и тесты каркаса не импортируют отсутствующий файл. Генерация пишет временный файл и заменяет выходной только при успехе; прежний экспорт не повреждается. Тест генератора использует временную минимальную OpenAPI-фикстуру, не объявляя её доменным контрактом проекта.

Альтернатива — ручной `schema.d.ts` или копия personas.json — создаёт второй источник истины. Полноценная интеграция и типизированные бизнес-хуки требуют отдельного изменения после экспорта Dev 2; текущий каркас завершается без ожидания этого экспорта.

### 6. Проверка поведения

- Vitest + Testing Library: переходы меню, активные ссылки, прямые маршруты, 404, пометка предварительного просмотра, отсутствие запросов из заглушек.
- Подменённый fetch: база/токен/JSON, защита адреса, 200/204, некорректный JSON, 401/403/409/422/502, сеть и отмена.
- Интеграционный тест сессии и QueryClient: 401 очищает данные и перенаправляет, устаревший 401 не затрагивает новую сессию.
- Генератор: понятная ошибка при отсутствии схемы, успешная генерация на временной фикстуре, сохранность прежнего файла при ошибке.
- Ручная браузерная проверка: desktop 1280/1440, клавиатура, refresh вложенного адреса, отсутствие ошибок консоли.

Все ответы транспорта в тестах синтетические и детерминированные; MSW и реальные внешние интеграции не нужны. Полный harness проверяет существующие backend-тесты и новый frontend; отдельно выполняется production build.

## Risks / Trade-offs

- [API не опубликован] → Типы и интеграция отложены явно; каркас не генерирует фиктивные решения и не обращается к отсутствующим endpoint.
- [Совместимость Alfa с React 18 и выбранным bundler] → Проверить peerDependencies и документированные стили перед фиксацией lock, выполнить production build и просмотр UI.
- [Превью двух контуров можно принять за авторизацию] → Постоянная пометка, отсутствие реальных данных и команд; предусмотреть будущий RequireRole без обещания защиты сейчас.
- [Существующий `.gitignore` игнорирует новые `openspec/` и `docs/`] → Не менять пользовательское правило в планировании; перед коммитом согласовать исключения или адресное включение артефактов. Сейчас коммит не создаётся.
- [Docker daemon недоступен] → Проверка этого изменения локальная через npm и harness; контейнерная поставка остаётся отдельной интеграцией.

## Migration Plan

Миграций БД и API нет. При apply создаётся новая папка frontend, зависимости устанавливаются из lock-файла; команда запуска описывается в frontend/README.md. Откат — отдельный revert будущего коммита с каркасом; существующие backend и документы требований не затрагиваются. Проектные спецификации синхронизируются только через archive после реализации, не во время propose.
