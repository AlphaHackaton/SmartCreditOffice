# Design

## Context

См. proposal.md. Основа frontend-shell реализована и проверена; её изменение завершено, но ещё не архивировано. Основных спецификаций пока нет. В коде уже есть AppLayout, placeholder-маршруты, транспорт createApiClient, SessionProvider с токеном в памяти, очистка QueryClient при 401 и генератор OpenAPI. Реального пользователя/роли, бизнес-хуков и экранов нет. Пользователь подтвердил, что API Dev 2 ещё разрабатывается.

Новый этап ведётся в `codex/frontend-client-flow` поверх коммитов frontend-shell. Требования SPEC и ARCHITECTURE не изменяются. План использует согласованные официальные отдельные пакеты Alfa, React 18 и существующий стек.

## Goals / Non-Goals

**Goals:**
- Подготовить пользовательский вход, защищённую навигацию и один положительный путь до серверной выдачи.
- Развести работу, доступную без API, и интеграцию, которая требует опубликованного контракта.
- Сохранять подтверждение состояний и все финансовые значения на стороне backend.

**Non-Goals:**
- Не реализовывать сервисы, моки, БД и скоринг вместо Dev 2/Dev 1.
- Не расширять этап до симулятора, ручного решения сотрудника и аналитики.
- Не выдавать локальные UI-фикстуры за API-контракт или работающий сквозной путь.

## Decisions

### 1. Этапы и зависимость от контракта

Этап A доступен без API: переименование служебного контура и самостоятельный LoginView с полями логина/пароля, локальным состоянием, доступностью и обработчиками через props. Поля формы — внутреннее представление UI, не декларация внешнего DTO. Компонент тестируется локально; успешный вход не симулируется.

Этап B начинается после готовности контракта. Список API-потребностей находится в API_HANDOFF.md. До подключения endpoint необходимо получить реальный docs/openapi.json, запустить gen:api, проверить схемы пользователя/роли, ошибок, заявки и подтверждения подписи. Затем доступны типизированные хуки, формы и отображение серверных данных.

Этап C — интеграционная проверка против stub. Требуется отдельное подтверждение, что переходы до DISBURSED работают через HTTP, а не только в unit-тестах. Обещанная дата API неизвестна; эта зависимость не заменяется задачей самостоятельной реализации backend.

Альтернатива — написать frontend DTO по архитектурным примерам — отвергнута: примеры в ARCHITECTURE не являются экспортом API и могут отличаться от реализации.

### 2. Названия и навигация

Пользовательские подписи: «Сотрудник банка», «Вход для сотрудников», «Рабочее место кредитного специалиста». Технические `/bank/*` и смысл роли BANK сохраняются; wire-значение роли берётся из фактической схемы, при необходимости нормализуется в одном адаптере.

До подключения входа существующий переключатель остаётся только помеченным предварительным просмотром с новой подписью. После подключения входа он убирается из авторизованного layout: показывается роль текущего пользователя, меню только его контура и кнопка выхода. Ссылка «Вход для сотрудников» на /login меняет контекст формы (например, query-параметром audience=employee), но не отправляет роль как источник полномочий.

После POST login выполняется GET me. Только затем клиент направляется на /client, сотрудник — на /bank/applications. Вход уже авторизованного пользователя ведёт в его пространство. Корневой redirect на /client сохраняется от shell; guard направляет сотрудника в его допустимое пространство. Неверный явный адрес другого контура показывает 403 и ссылку домой. Сохранённый после входа returnTo допускается только как локальный путь разрешённой роли.

### 3. Сессия и защита

SessionProvider расширяется сведениями о текущем пользователе и состояниями anonymous/loading/authenticated. Полученный токен сохраняется только в памяти. Пока GET me не подтвердил роль, данные компаний/заявок не запрашиваются; неизвестная роль не открывает контур. При ошибке подтверждения пользователю не показывается контент другой роли.

RequireRole проверяет состояние пользователя перед рендером дочерних маршрутов, а серверный RBAC остаётся обязательным. При logout/401 удаляются токен, пользователь и кеш, отменяются запросы. Существующая защита от позднего 401 дополняется защитой от позднего GET me/логина предыдущей попытки: отмена и проверка идентификатора актуальной попытки. Логи не содержат пароли, токены или полные тела ошибок.

Перезагрузка требует повторного входа, как и в shell. Альтернатива — localStorage — не выбирается: автоматическое восстановление не нужно для текущего демо и изменило бы принятую модель хранения.

### 4. API и модели данных

В этом изменении новые endpoint, схемы backend и модели БД не создаются. Таблица ниже — потребности по ARCHITECTURE:580–593, 740–749, которые Dev 2 должен подтвердить экспортом. Формат login (JSON или form), имя полей/enum роли, обязательная версия команд и структура SigningChallenge не угадываются.

| Потребность | Ожидаемая операция под /api/v1 | Что должно быть подтверждено OpenAPI/stub |
|---|---|---|
| Вход и текущий пользователь | POST auth/login; GET auth/me | Формат входа, токен, пользователь, роль, ошибки |
| Демо-вход | GET demo/personas | Список тестовых учёток без копии seed во frontend |
| Кабинет | GET companies/me; GET products; GET applications | Компания, продукты, ограничения суммы/срока, заявки |
| Создание и чтение заявки | POST applications; GET applications/{id}; при необходимости PATCH applications/{id} | Деньги-строки, цель/согласия, requested, status, version, history |
| Подача | POST applications/{id}/submit | Версия/идемпотентность и последующий серверный статус |
| Принятие условий | POST applications/{id}/accept | Оффер, срок действия, версия, вызов подтверждения |
| Подпись | POST applications/{id}/sign | Серверный код внутри UI, ошибки кода, восстановление/повтор challenge |

GET конкретной заявки требуется поллингу и подтверждается отдельно: таблица архитектуры перечисляет его неявно, хотя useApplication(id) предполагает чтение. Значения рейтингов/примерные условия seed не кодируются во frontend. Факторы отображаются через client_text/hint фактического API, без сырого БКИ, внутренних порогов и банковской трассы. Правила, веса и пороги скоринга не меняются и не переносятся во frontend.

Ключи TanStack Query содержат идентичность текущего пользователя/компании. Бизнес-хуки используют generated components/operations; fixtures типизированы ими. При 409 команда не повторяется, инвалидируется текущая заявка и показывается сообщение о конфликте. 422 привязывается к полям по опубликованному ErrorDTO. 403/404 показывают недоступность без утечки данных.

### 5. Экран заявки и UI-состояния

DashboardPage читает профиль, продукты и заявки независимо: ошибка одной секции не подменяет её нулевыми показателями. NewApplicationPage управляет суммой/сроком/целью и обязательными согласиями. Деньги редактируются как десятичные строки с проверкой формата и ограничений продукта; расчёт платежа отсутствует. При создании и submit кнопки блокируются, а маршрутизация использует только возвращённый id. Порядок create/patch/submit определяется опубликованным API и не скрывает серверные переходы.

ApplicationPage выбирает панель по сгенерированному статусу. Предусмотрены DRAFT, SUBMITTED, SCORING, UNDERWRITING, APPROVED, COUNTER_OFFER, REJECTED, SIGNING, SIGNED, DISBURSED, CANCELLED, EXPIRED; карта exhaustive после генерации enum. Неожиданный runtime-статус показывает контролируемую ошибку и отключает команды. История — только серверные события; даты UTC отображаются через Europe/Moscow.

Поллинг 1500 мс для SUBMITTED/SCORING/SIGNED и 3000 мс для UNDERWRITING; прекращается при уходе, ошибке доступа, logout и финальном статусе. Переход в SIGNING не делает новый accept автоматически; challenge хранится в памяти для текущей заявки. После refresh сессия завершается и требуется повторный вход; возвращённый из API статус SIGNING должен иметь документированный способ получить challenge повторно без незаконного перехода FSM. Это обязательный пункт готовности API.

Для APPROVED показываются сумма, срок, ставка, платёж, переплата, expiry и клиентские факторы. formatMoney работает со строками без parseFloat/финансовых вычислений. Местная проверка expiry отключает принятие истёкшего оффера, окончательное решение остаётся за сервером. accept и sign выполняются однократно по явному действию. Успех подписи может вернуть SIGNED; «Кредит выдан» появляется только при DISBURSED.

COUNTER_OFFER, REJECTED и UNDERWRITING отображаются информативно без реализации новых команд и симулятора. CANCELLED/EXPIRED — завершённые состояния. Обработчики статусов не присваивают app.status локально.

### 6. Структура и проверки

Используются существующие AppProviders, API transport, QueryClient и layout. Добавляются auth/LoginView, LoginPage, RequireRole; api/keys, queries и типизированные адаптеры; shared/format, status, StatusBadge, Timeline, FactorList; client/DashboardPage, NewApplicationPage, ApplicationPage и панели одобренного пути. Только нужные отдельные Alfa-пакеты добавляются с lock/notices; стек не меняется.

Тесты рядом с каждым этапом: LoginView без API; затем auth/RBAC и изоляция сессий; формат денег и дат; ограничения формы; серверные статусы и остановка поллинга; accept/sign, неверный код, expiry/409; положительный HTTP-путь Соколовой против stub. Ответы внешних ФНС/БКИ/выручки — локальные детерминированные моки Dev 2. Во frontend нет MSW-сервера, собственной копии персон и денежных формул.

## Risks / Trade-offs

- [OpenAPI и stub ещё отсутствуют] → Этап A можно делать независимо; этапы B/C и завершение изменения заблокированы до передачи API. Не отмечать интеграционные задачи выполненными.
- [Таблица endpoint и DTO архитектуры отличается от API] → Сверить API_HANDOFF.md с экспортом до интеграции; существенное расхождение отразить через update-change, не править сервер скрытно.
- [Повтор accept после сбоя/повторного входа] → Требовать документированный способ восстановить challenge при SIGNING; не повторять изменяющие команды автоматически.
- [Клиент принимает название «Сотрудник банка» за выдачу прав] → Роль подтверждает GET me, сервер проверяет доступ; подписи и URL не определяют полномочия.
- [Предшественник ещё не архивирован] → Не редактировать openspec/specs вручную. При архивировании последовательно синхронизировать shell, затем новые возможности; договорённости shell об отсутствии входа описывают его исторический этап, а не запрет последующих фич.

## Migration Plan

Выполнять коммиты по завершённым задачам. Этап A сохраняет автономность каркаса. После готовности схемы сгенерировать типы, подключить серверные данные и заменить только соответствующие placeholders. Нереализованные служебные страницы остаются явно обозначенными заглушками за guard. Миграций БД нет; rollback — revert frontend-коммитов без удаления данных/миграций backend. Полное закрытие — только после HTTP-сценария, build, harness exit 0 и OpenSpec strict.
