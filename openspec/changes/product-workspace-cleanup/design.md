# Design

## Context

См. proposal.md. Существуют отдельные представления для HTTP и автономного источника. LoginView уже поддерживает ручной ввод. AppLayout монтирует DemoControls и ApiNotice для всех посетителей.

## Goals / Non-Goals

**Goals:** единая продуктовая оболочка; сохранить обе роли, доступные действия и прозрачность решений.

**Non-Goals:** изменение API, схем, модели данных, финансовой логики, зависимостей и инфраструктуры.

## Decisions

- Удалить монтирование DemoControls и ApiNotice, запрос персон и быстрые входы. Инструменты и транспорт остаются для существующих тестов. Источник выбирается конфигурацией окружения; UI не переключает его.
- На входе показывать только форму и описание кабинета; sidebar появляется после авторизации. Роль подтверждается существующим AuthProvider.
- Оба набора страниц используют продуктовые подписи. Убрать технические версии/хеши из сводки клиента. В досье сохранить риск-политику, правила, факторы, финансовые исходные данные и аудит.
- JSON в HTTP-досье заменить рекурсивным представлением полей с подписями и раскрытием вложенных групп. Не подставлять выдуманные данные при отсутствии сведений.
- Сохранить анализ условий и сравнение политик в банковском контуре под понятным названием; не показывать недоступный пункт в HTTP-режиме, прямой маршрут объясняет недоступность.
- Скоринг не меняется: факторы, веса и пороги приходят из существующего доменного движка без вычислений во frontend.

## Risks / Trade-offs

- Тесты опираются на демо-кнопки и технические надписи → перевести интеграционные проверки на ручной вход и продуктовые названия, оставить тесты изолированных инструментов.
- HTTP и автономный источники поддерживают разные действия → сохранить существующие возможности каждого, не добавлять fallback.
- Утрата объяснения при очистке → сохранять все поля решения и аудита в читаемом представлении.
