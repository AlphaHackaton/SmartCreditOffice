## 1. Развертывание, инфраструктура и аппаратные требования

### 1.1. Как должно запускаться решение? Обязателен ли Docker?
* **Вопрос:** В требованиях написано про запуск решения через Docker. Каковы обязательные условия запуска?
* **Ответ организаторов:** Решение должно запускаться воспроизводимо в Docker (Docker Compose). Публикация в облаке / на сервере желательна для демонстрации, но возможность локального запуска экспертами на обычном ПК через Docker обязательна.

### 1.2. Можно ли запускать LLM (например, Ollama) вне Docker?
* **Вопрос:** Можно ли оставить запуск LLM через Ollama вне Docker для быстродействия?
* **Ответ организаторов:** Да, можно оставить запуск LLM через Ollama вне Docker. В `README.md` необходимо подробно описать установку и запуск Ollama, используемую модель и параметры подключения к ней, чтобы эксперты могли воспроизвести решение. Все остальные компоненты системы должны запускаться в Docker.

### 1.3. На какие аппаратные характеристики ориентироваться при проверке экспертами?
* **Вопрос:** На какое железо организаторов ориентироваться? Есть ли ограничения по ресурсам?
* **Ответ организаторов:** Ориентируйтесь на характеристики стандартного офисного ПК: **8–16 ГБ оперативной памяти**, **без обязательного наличия дискретной видеокарты** (CPU-only). Решение должно успешно запускаться в таких условиях.

### 1.4. Можно ли разместить решение на внешнем (платном) VPS для демонстрации?
* **Вопрос:** Во время демонстрации проект может работать на платном VPS?
* **Ответ организаторов:** Да, для демонстрации можно разместить проект на VPS (в том числе платном), чтобы предотвратить проблемы при запуске. При этом обязательно сохраните и задокументируйте в `README.md` возможность локального запуска решения в Docker на обычном ПК.

### 1.5. Обязателен ли REST API со Swagger или допустим GraphQL?
* **Вопрос:** Обязателен ли REST со Swagger или можно использовать GraphQL + GraphQL Schema + GraphiQL / Apollo Sandbox?
* **Ответ организаторов:** REST со Swagger не является строго обязательным, GraphQL и другие подходы допустимы при наличии понятной документации/схемы API.

## 2. Искусственный интеллект, LLM и скоринг

### 2.1. Обязательно ли использовать ИИ в решении и даёт ли это баллы?
* **Вопрос:** Обязательно ли внедрять ИИ / локальную нейросеть / ИИ-ассистента? Добавляет ли ИИ дополнительные баллы?
* **Ответ организаторов:** Использование ИИ/LLM **не является обязательным**. Само по себе наличие ИИ не даёт дополнительных баллов. Важна ценность решения для пользователя и бизнеса: если ассистент или ИИ реально помогает пройти кредитный путь, упрощает действия или ускоряет процесс, это усиливает решение. Основной сквозной сценарий кредитного конвейера должен оставаться работоспособным и без ИИ.

### 2.2. Предоставляются ли API-ключи к моделям от Альфа-Банка?
* **Вопрос:** Где получить API-ключ на команду для доступа к модели (например, Qwen), выдадут ли токены?
* **Ответ организаторов:** В треке «Умный кредитный кабинет» ключи доступа к моделям и токены **не предоставляются** (выдача ключей производилась только для других треков хакатона).

### 2.3. Какие модели разрешено использовать и каковы ограничения?
* **Вопрос:** Какие модели нейросетей разрешены? Можно ли использовать внешние API (Groq, OpenRouter, Yandex Cloud и др.)?
* **Ответ организаторов:**
  * Разрешены **только модели с открытыми весами (Open Weights)**: например, семейства Qwen, Llama, Mistral, Gemma, DeepSeek. Платные закрытые модели (GPT-4, Claude, закрытые платные API) запрещены.
  * Проверяемая версия решения **не должна зависеть от платных подписок и платных API**, даже если они оплачены самой командой.
  * Использование бесплатного стороннего API для доступа к LLM с открытыми весами **допустимо**, если:
    1. Интеграция совместима с OpenAI API (позволяет переопределить `base_url`, `api_key` и имя модели).
    2. Эксперты при проверке могут без изменения кода подключить собственного провайдера или локальный инстанс.
  * Для разработки вы можете использовать любые инструменты, но в сдаваемом решении действуют правила автономности и открытых весов.

### 2.4. Есть ли ограничения на размер весов LLM?
* **Вопрос:** Ограничение весов модели 120 млрд параметров — это активные параметры или общий вес модели?
* **Ответ организаторов:** Рекомендация использовать модели до 120 млрд параметров относится к общему количеству параметров модели. При этом 120B — не жесткое ограничение, а рекомендация с учетом ресурсов и времени отклика.

### 2.5. Предоставляются ли банком исторические датасеты заявок для скоринга?
* **Вопрос:** Мы сами решаем, по каким параметрам одобрять кредит? Предоставляются ли референсные данные заявок?
* **Ответ организаторов:** Логику кредитного скоринга команда определяет самостоятельно, допускается упрощенная логика принятия решений. Банк не предоставляет датасеты одобренных заявок. Тестовые и демонстрационные данные команды формируют сами.

## 3. Бизнес-логика, архитектура процесса и интеграции

### 3.1. Интеграции с банковскими CRM и внешними сервисами
* **Вопрос:** Под какие CRM-системы Альфа-Банка делать решение? Предоставляются ли доступы или учетные записи сотрудников банка?
* **Ответ организаторов:** Привязка к реальным внутренним CRM Альфа-Банка не требуется. Доступ к корпоративным системам банка не предоставляется. Необходимые внешние проверки и сервисы (CRM, ФНС, БКИ, скоринг) моделируются с помощью **моков (mock) или симуляторов**.

### 3.2. Что приоритетнее — клиентская часть или внутренняя банковская?
* **Вопрос:** Проработана должна быть больше клиентская часть или банковская?
* **Ответ организаторов:** Приоритет кейсом не определяется. Важно показать связанный процесс: клиент подает заявку и получает результат, а банковская логика обрабатывает данные и принимает решение. Глубину проработки команда определяет в рамках MVP.

### 3.3. Классический конвейер или принципиально новый сценарий?
* **Вопрос:** Что важнее: качественно реализовать существующий кредитный процесс или предложить принципиально новый пользовательский сценарий?
* **Ответ организаторов:** Оба подхода допустимы. Важны целостность и работоспособность решения, его ценность для клиента и банка, обоснованность решений. Новизна приветствуется, но не заменяет качественную реализацию основного сквозного сценария.

## 4. Клиентский путь, роли и интерфейс (UX / UI)

### 4.1. Формат приложения: Веб vs Мобильное
* **Вопрос:** Допускается ли мобильное приложение или кроссплатформенная разработка?
* **Ответ (из регламента и обсуждения кейса):** Клиентская часть решения обязательно должна быть реализована в виде **веб-интерфейса**. Реализация продукта в виде мобильного приложения **не допускается**.

### 4.2. Нужен ли отдельный веб-интерфейс для сотрудника банка?
* **Вопрос:** В ТЗ сказано про участие сотрудника банка при нестандартных ситуациях. Нужно ли писать отдельный веб-интерфейс для сотрудника?
* **Ответ организаторов:** Отдельный веб-интерфейс для сотрудника банка **не является обязательным**. Однако логика обработки заявки на стороне банка **обязательна**: необходимо показать движение заявки по этапам, ее обработку и принятие решения. Можно реализовать и клиентскую, и банковскую логику в рамках одного веб-интерфейса (например, с переключением ролей). Главное — обеспечить сквозной рабочий процесс.

### 4.3. Авторизация, онбординг и ввод данных юрлица/ИП
* **Вопрос:** Нужно ли реализовывать регистрацию/вход с вводом реквизитов компании (ИНН, ОГРН, учредители)?
* **Ответ организаторов:** Обязательная регистрация не требуется. По условиям кейса предполагается, что предприниматель **уже является клиентом банка**, поэтому основные сведения о компании уже есть в системе. Повторную регистрацию и сбор пакета документов реализовывать не нужно. Экран авторизации/входа не обязателен — можно сделать упрощенный вход (например, по номеру) или сразу открывать демонстрационный предзаполненный профиль.

### 4.4. Допустимы ли внешние каналы (SMS, Email, Telegram, звонки)?
* **Вопрос:** Можно ли сделать подтверждение или вход по SMS / Email кодом?
* **Ответ организаторов:** Нет. Основной пользовательский сценарий должен полностью проходить **внутри продукта**. Электронная почта, мессенджеры, SMS и звонки **не должны** быть частью сценария прохождения конвейера.

### 4.5. Адаптивная верстка
* **Вопрос:** Делать ли веб-сайт с учетом адаптивной верстки под разные экраны?
* **Ответ организаторов:** Адаптивная верстка **не является обязательным требованием** к решению.

### 4.6. Требуется ли лендинг?
* **Вопрос:** Требуется ли в решении публичный лендинг с переходом в ЛК?
* **Ответ организаторов:** По желанию команды, требования нет.

### 4.7. Дизайн-система и фирменный стиль
* **Вопрос:** Обязательно ли оформлять проект в стиле Альфа-Банка и где взять компоненты?
* **Ответ:** Строгих ограничений нет (дизайн на усмотрение команды), однако использование стиля банка приветствуется. Доступна открытая дизайн-система банка: [Alfa Bank Core Components](https://core-ds.github.io/core-components/master/?path=/docs/intro--docs).

## 6. Требования к составу репозитория и формат сдачи

### 6.1. Дедлайн сдачи
* **Срок:** **26 октября 2026 года до 18:00 по московскому времени**. Коммиты после дедлайна жюри не учитываются.

### 6.2. Доступ к репозиторию для жюри
* Для приватных репозиториев на GitHub необходимо выдать доступ аккаунту: `alfa-hack-2026` (достаточно прав на чтение и клонирование: Read/Clone).

### 6.3. Обязательные файлы и документация в репозитории
1. **`README.md`**: описание решения, архитектурная схема, требования к окружению, переменные `.env`, пошаговая инструкция запуска в Docker (и Ollama, если вынесена), сценарий проверки.
2. **`THIRD_PARTY_NOTICES`**: обязательный файл со списком всех сторонних библиотек, компонентов, фреймворков, открытых моделей, датасетов и смоделированных интеграций (создается даже при отсутствии ИИ).
3. **Lock-файлы зависимостей**: фиксация версий библиотек (package-lock.json, poetry.lock, requirements.txt с пинами и т.п.).
4. **Спецификация API**: OpenAPI/Swagger схема, коллекция Postman/Bruno/схема GraphQL.
5. **Тестовые синтетические данные**: демонстрационные учетные записи, предзаполненные юрлица и заявки для сквозного прогона сценария.

### 6.4. Нужна ли презентация и видео?
* **Ответ организаторов:** В рамках отборочного этапа требуется **только техническое решение**. Презентация **не требуется**. Демонстрационное видео прохождения сценария рекомендуется, но остается на усмотрение команды (без жестких ограничений по формату и длительности).

### 6.5. Как сдавать решение на платформе при лимите 18 МБ?
* **Вопрос:** На платформе ограничение 18 МБ и нет отдельного поля для ссылки на GitHub. Как загрузить решение?
* **Ответ организаторов:** Можно сдать:
  * Презентацию/PDF-документ из одного слайда/страницы, где будут указаны все ссылки (GitHub-репозиторий, задеплоенный стенд, видео);
  * Либо ZIP-архив с текстовым файлом (`README.txt` / `links.txt`), содержащим ссылки на репозиторий и демо;
  * Либо git-архив с исходным кодом, если он укладывается в 18 МБ.
