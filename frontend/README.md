# Frontend — кредитный кабинет

Node.js 22.12+ (проверено на 24.21), React 18, TypeScript strict, Vite, Alfa Core Components, TanStack Query и react-router. Из корня:

```bash
npm ci --prefix frontend
npm run dev --prefix frontend
npm test --prefix frontend -- --run
npm run lint --prefix frontend
npm run typecheck --prefix frontend
npm run build --prefix frontend
```

http://localhost:5173. Только desktop. Официальные отдельные Alfa-пакеты совместимы с React 18; стили локальные.

## HTTP API — основной режим

По умолчанию приложение использует настоящий `/api/v1` через Vite proxy на localhost:8000. Запустите backend в отдельном терминале:

```bash
UV_CACHE_DIR="$PWD/tmp/uv-cache" uv sync --project backend --frozen
APP_MODE=stub uv run --project backend uvicorn app.main:app --app-dir backend --reload
npm run gen:api --prefix frontend
npm run dev --prefix frontend
```

`APP_MODE=stub` — настоящий HTTP с доменным Python engine и хранением в памяти, без БД. `APP_MODE=real` использует PostgreSQL; контракты и frontend одинаковы. Учётки `p1`…`p6`, сотрудник `underwriter`, пароль `demo`; роль подтверждается `/auth/me`. Токен хранится только в памяти. Перезагрузка требует нового входа, заявки сохраняются на стороне сервера (до перезапуска stub).

Подключены все **21 опубликованная HTTP-операция**: health/personas/login/me, профиль с предварительным лимитом, каталог, собственные заявки, create/PATCH/submit/simulate/accept/sign/cancel, банковская очередь/досье/scoring-runs/decision/rescore/метрики, reset. Карточка клиента читается из собственного списка: GET `/applications/:id` отсутствует. Денежные значения передаются строками; в JS нет расчёта скоринга/платежей/ставок. Оффер принимается после подтверждения с `offer_id` и `version`; код из `SigningChallenge` вводится внутри UI, `sign` передаёт только `{code}` и актуальную query-version. Опрос ждёт настоящий `DISBURSED`. Симулятор debounce 300 мс, отменяет старые запросы и скрывает старый прогноз; симулированные предложения не подменяют офферы заявки.

Черновик можно отредактировать из карточки. После неудачного submit повтор использует тот же созданный id. Автоповтора команд нет; 401 очищает только соответствующую сессию, ошибки сохраняют ввод. Перед отменой/решением/пересчётом/сбросом требуется подтверждение. Reset удаляет серверные демонстрационные данные всех пользователей — кнопка предупреждает об этом.

Ограничения опубликованного контракта: согласия проверяются в UI, сервер их не принимает/не сохраняет; ApplicationOut не содержит purpose/created_at. В SIGNING после reload API не восстанавливает код (нет challenge endpoint): интерфейс предлагает отменить заявку и начать новую. В bank DTO нет названий компаний/ИНН, выбора оффера/версии команды, расширенных KPI/фильтров метрик. Не имитируем эти поля. В stub нет сохранённых scoring-runs/inputs; rescore только пишет аудит. Sandbox, replay и подготовленные presets/failure injection доступны в **Mock**, а не через несуществующие HTTP endpoints. API-ошибка никогда не включает fallback на Mock.

## Данные и домен

```bash
npm run gen:demo --prefix frontend
```

Генератор `scripts/export_frontend_demo.py` читает backend seed, POLICY_V1, enum и FSM и создаёт `src/demo/generated.ts`. Персоны/продукты/статусы не переписываются вручную; истории проверяются настоящим Python FSM. В браузер попадают публичные профили и готовые последовательности стадий, без банковской трассы. Для произвольных условий финал демо — ручное рассмотрение, без локального расчёта решения.

Полная проверка выполняет генератор с `--check`: изменение backend seed/enum/политики без регенерации frontend-артефакта завершает harness с ошибкой. Таким образом, устаревшие фикстуры не проходят проверку.

MockGateway хранит данные и сессии только в памяти, проверяет роль/владельца/version, возвращает копии, отменяет чтения через AbortSignal, отклоняет старые команды после reset и не повторяет команды автоматически. BigInt используется только для точной проверки границ/шага ввода и сравнения сумм при сортировке; ставки, платежи и скоринг в JS отсутствуют.

## Вход и навигация

`/login` подключён к готовой LoginView. Демо-учётки загружаются адаптером: `p1`…`p6` из backend seed, сотрудник `underwriter`; пароль `demo`. Можно войти формой или кнопкой персоны. Это синтетическая демонстрация, реальные пароли вводить не нужно.

AuthProvider проверяет текущего пользователя через адаптер и определяет роль по ответу; подпись «Вход для сотрудников» прав не выдаёт. RequireRole блокирует защищённые запросы до подтверждения пользователя. Путь после входа восстанавливается только внутри собственного контура; внешние URL, traversal и адреса чужой роли отклоняются. Выход/401 отменяют запросы и очищают кеш, запоздалый вход после выхода/reset сессию не создаёт. Пароль и токен не сохраняются в localStorage/sessionStorage.

Клиент: `/client`, `/client/applications/new`, `/client/applications/:id`. Сотрудник: `/bank/applications` — очередь; `/bank/applications/:id` и `/bank/metrics` пока честные заглушки. Досье/решение/метрики — следующие фичи. Переключателя прав в layout нет, доступны только ссылки своей роли. Неизвестный адрес — 404.

## Общие компоненты

- `shared/format.ts`: formatMoney, formatPct, formatDate, formatDateTime. Денежные строки без Number/parseFloat, две копейки и U+00A0; лишняя точность отклоняется. Проценты без умножения на 100/округления. Календарь YYYY-MM-DD без сдвига, события с timezone — Europe/Moscow. Неверные/пустые значения → `—`.
- MoneyText(value) и DateTimeText(value, kind='timestamp'|'date'): табличные цифры, семантический time/dateTime и доступное описание недоступных данных.
- ErrorBanner(message, onRetry?, pending?): безопасный alert, повтор по нажатию, защита дублей и отклонения Promise.
- ConfirmDialog(open, title, description, confirmLabel, onConfirm, onCancel, pending?): Alfa-кнопки и нативная модальность, фокус отмены, Tab/Shift+Tab внутри, Escape/возврат фокуса, блокировка во время Promise и безопасная ошибка. В jsdom модальность проверяется отдельной заглушкой; браузерная проверка обязательна.

## HTTP-транспорт и будущий OpenAPI

`useApiClient()` — `/api/v1`, Bearer из памяти, JSON со строками сумм, AbortSignal, запрет внешнего URL/traversal/redirect. ApiError сохраняет status/code/message/details; 204 возвращает undefined, плохой JSON — INVALID_RESPONSE, сеть — NETWORK_ERROR. Только 401 текущей сессии очищает токен/кеш; 403/409/422 его сохраняют. Отменённый запрос не превращается в сетевую ошибку, автоматических повторов команд нет. Vite проксирует `/api` на localhost:8000.

```bash
npm run gen:api --prefix frontend
```

Генерирует `src/api/schema.d.ts` только из настоящего `docs/openapi.json`. При отсутствии экспорта Dev 2 команда возвращает понятную ошибку; при ошибке сохраняет прежний результат. Фиктивного OpenAPI нет. Финальная адаптация auth/команд/версий к HTTP требует отдельной проверки после передачи API.

Сведения о зависимостях: `npm run notices --prefix frontend`, версии фиксированы package-lock.json.

## Кабинет клиента

DashboardPage независимо загружает профиль, продукты и заявки через TanStack Query. Ключи включают режим, поколение демо и пользователя; AbortSignal отменяет чтения. Ошибка одной секции не скрывает остальные, повтор выполняется кнопкой. Продукты показывают границы политики без выдуманной ставки/предодобренного лимита. Выбор продукта передаёт query-параметр форме; список заявок ведёт на прямые адреса. Новая компания начинает с пустого списка.

## Новая заявка и черновики

NewApplicationPage принимает `?product=CODE` или `?draft=ID`. Поля: продукт, сумма-строка, целый срок, цель, согласия БКИ/ПД. Границы и шаг берутся из политики backend. Черновик можно сохранить без согласий; подача требует оба. Ошибка 422 показывается у поля без потери ввода. Повтор после неудачного submit обновляет тот же draft, не создаёт второй. Version проверяется адаптером; при конфликте читается актуальная версия без автоматического повтора команды. После успешной подачи открывается возвращённый id; двойной клик блокируется. Смена пользователя/уход со страницы не позволяют запоздалой мутации перенаправить новый экран.

## Страница заявки

ApplicationPage читает собственную заявку, показывает запрошенные условия, текущий статус и Timeline. Для DRAFT доступно продолжение по `?draft=ID`. SUBMITTED/SCORING и SIGNED опрашиваются каждые 1500 мс; ошибка, результат, logout или уход прекращают опрос. Ошибка чтения повторяется явно; 403/404 скрывают данные. Неизвестный runtime-статус не открывает действия. Демо воспроизводит backend-историю до APPROVED/COUNTER_OFFER/REJECTED/UNDERWRITING; офферы, подписание, симулятор и очередь реализованы ниже; доступные HTTP-команды описаны выше.

## Фича 7: одобрение и офферы

DecisionPanel/FactorList показывают публичные объяснения Python, OffersList — готовые денежные строки, ставку, срок, платёж, переплату и срок действия (в демо 30 минут). ## Фича 8: подписание и выдача

После accept открывается SigningPanel с неизменяемыми выбранными условиями и кодом 123456 внутри UI. Подтверждение живёт 5 минут, допускает 3 неверных попытки; после блокировки новый сценарий начинается сбросом демо. Возврат по адресу восстанавливает challenge в текущей сессии. sign возвращает SIGNED, опрос через 1500 мс получает DISBURSED и останавливается. Только этот статус открывает «Кредит выдан». Это виртуальная подпись/выдача без внешних каналов.

## Фича 9: контроффер и симулятор

COUNTER_OFFER показывает исходный запрос, готовые альтернативы и ограничивающие условия Python. Симулятор есть также при APPROVED: debounce 300 мс, отмена предыдущего чтения, состояние обновления без устаревшего прогноза. Сумма передаётся строкой, срок — целым; выберите подготовленную сумму из списка и срок ползунком. В сетке исходная/минимальная/половинная/альтернативные суммы и все сроки с шагом 6; другие комбинации дают явную ошибку «нет демо-расчёта». Результаты simulate заранее экспортированы Python, не меняют заявку и не создают принимаемый оффер. Ограничения подсвечены, деньги/ставки/платежи в JS не вычисляются.

## Фича 12: кредитное досье, скоринговая трасса, ручное решение и аудит

По адресу `/bank/applications/:id` сотруднику доступно полное кредитное досье:
- **Параметры и входы:** запрошенные сумма/срок/продукт, версия и хеш снимка. `InputsSnapshot` отображает статус юрлица, блокировку счетов, отчётность ФНС, реестр договоров и просрочек БКИ, выписки по счетам и расчётные метрики. Недоступные данные отображаются как `—`, без превращения `null` в `0`.
- **Скоринговая трасса:** `ScoringTrace` показывает рекомендацию ядра, маршрут, кредитный грейд, баллы, лимитирующие ограничения (DSCR, выручка, потолки продукта/грейда), а также детальную скоринговую карту факторов (M1–M5 и стоп-правила `KO_*`) с бинами и границами из Python-политики.
- **Сверка снимка (Replay):** кнопка выполняет детерминированную сверку хешей входных данных и скорингового результата с расчётным ядром Python без возврата заявки в скоринг.
- **Ручное решение андеррайтера:** `DecisionForm` доступна только для заявок в статусе `UNDERWRITING`. Андеррайтер выбирает допустимый исход (`APPROVED`, `COUNTER_OFFER`, `REJECTED`), готовое кредитное предложение из подготовленной сетки и вносит обязательный комментарий (1–2000 символов). Если решение расходится с рекомендацией ядра, система предупреждает об `OVERRIDE`. Перед фиксацией открывается модальный диалог подтверждения.
- **Журнал аудита:** `AuditLog` фиксирует каждое ручное решение, исполнителя, московское время, комментарий, переход версий и признак переопределения. Внутренний комментарий и банковские входы не попадают в клиентскую проекцию.
- **Сквозной сценарий P6:** клиент создаёт заявку P6 (`UNDERWRITING`) → андеррайтер открывает досье и утверждает решение → клиент видит оффер в своём кабинете, подтверждает выбор, подписывает кодом и получает статус `DISBURSED`. Для регрессионного review-варианта P6 (CAPEX 6 млн / 24 мес) система строго ограничивает одобрение запрошенных условий из-за норматива DSCR и допускает только встречное предложение (`COUNTER_OFFER`).

## Фича 13: операционные метрики конвейера (Pipeline Metrics)

По адресу `/bank/metrics` сотруднику доступна операционная аналитика рассмотрения заявок:
- **Когорта и фильтрация:** аналитический снимок фильтруется по источнику (`all` — все данные, `example` — синтетические примеры, `session` — заявки текущего сеанса), кредитному продукту и календарному периоду создания по московскому времени (`Europe/Moscow`, UTC+3) на полуинтервале `[00:00:00 даты с, 00:00:00 дня после даты по)`. Некорректные диапазоны валидируются с понятной ошибкой (обе даты обязательны или обе пусты, начало не позже окончания).
- **Ключевые показатели когорты:**
  - `total`: общее количество уникальных заявок в выбранной когорте.
  - `submitted`: количество заявок, имеющих этап `SUBMITTED` в истории.
  - `decided`: количество заявок с первым зафиксированным исходом (`APPROVED`, `COUNTER_OFFER`, `REJECTED`). Рекомендация скоринга при `UNDERWRITING` решением не считается до утверждения андеррайтером.
  - `awaitingDecision`: количество заявок, находящихся на рассмотрении в текущий момент (`SUBMITTED`, `SCORING`, `UNDERWRITING`).
  - `STP` (Straight-Through Processing): доля заявок с автоматическим решением `SYSTEM` (без вмешательства `BANK` до решения) среди всех принятых решений (`automaticDecisions / decided * 100`, один знак после запятой; при `decided = 0` отображается `—`).
  - `mean` и `p95` времени до решения: интервал от первого `SUBMITTED` до первого бизнес-решения (включая ручную проверку, без этапов подписания и выдачи). p95 вычисляется методом nearest-rank (`ceil(0.95 * N)`). Некорректные метки времени (отрицательная длительность, отсутствие даты подачи) исключаются из расчёта длительности и увеличивают счётчик проблем данных (`dataIssuesCount`).
- **Распределения:**
  - **Текущие статусы:** горизонтальная гистограмма и таблица со всеми статусами когорты (сумма бакетов строго равна `total`). Для каждого статуса доступна кнопка сквозного перехода в очередь (`/bank/applications?status=...&product=...&source=...&from=...&to=...`), при котором количество заявок в очереди совпадает с количеством в бакете.
  - **Принятые решения:** распределение первого бизнес-исхода (`APPROVED` — зелёный, `COUNTER_OFFER` — янтарный, `REJECTED` — красный). Исход остаётся зафиксированным и не затирается последующими этапами `SIGNING`, `SIGNED`, `DISBURSED`, `CANCELLED` или `EXPIRED`.
- **Согласованность и инвалидация:** метрики рассчитываются из единого хранилища заявок и историй. Ручное решение андеррайтера по заявке P6 атомарно переводит её из `awaitingDecision` в `decided`, снижает STP с 100% до 83.3% и увеличивает выбранный исход. Сброс демо восстанавливает исходный бейзлайн (6 заявок, 5 решений, 1 на рассмотрении, STP 100.0%). Повторная сверка (replay) досье не влияет на метрики. Клиентский доступ изолирован (403 `FORBIDDEN`), API-режим возвращает 503 `API_NOT_CONFIGURED`.

## Фича 14: каталог сценариев, инжектор сбоев и песочница скоринга

В панели «Управление демо» и банковском контуре реализован расширенный инструментарий демонстрации:
- **Каталог 12 сценариев:**
  - `p1-draft`: Черновик P1 (ООО «Вектор», сохранение и подача).
  - `p1-approved`: Одобрение P1 (готовые офферы и выбор предложения).
  - `p1-signing`: Подписание P1 (активный SMS-код 123456 и таймер 5 минут).
  - `p1-signed`: Подписано P1 (опрос до автоматической выдачи `DISBURSED`).
  - `p1-expired`: Истёкший оффер P1 (блокировка подписания по таймауту).
  - `p1-disbursed`: Выданный кредит P1 (финальный экран «Кредит выдан»).
  - `p2-counter`: Встречное предложение P2 (ИП Смирнов, симулятор и новые условия).
  - `p3-counter`: Встречное предложение P3 (ООО «Альфа Трейд», ограничения по лимиту).
  - `p4-rejected`: Отказ P4 (ООО «СтройКомплект», стоп-факторы БКИ/ФНС).
  - `p5-rejected`: Отказ P5 (ООО «Новые Технологии», молодой бизнес и дата повторной подачи).
  - `p6-review`: Ручное рассмотрение P6 (ООО «ПромСнаб», досье, скоринг и решение андеррайтера).
  - `factory-default`: Исходное состояние демо (6 фабричных примеров).
  При смене сценария в активной сессии или при наличии несохранённых данных запрашивается явное подтверждение. Загрузка сценария атомарно заменяет датасет, сбрасывает сессию и инвалидирует все TanStack Query кеши. Пресет не авторизует автоматически и не подменяет роли.
- **Адресный инжектор сбоев:**
  - Позволяет запланировать одноразовый сбой для конкретной операции: `any` (любая), `read` (конкретное чтение: `me`, `products`, `applications`, `application`, `preview`, `dossier`, `metrics_read`, `queue_read`, `sandbox_catalog`, `sandbox_run`) или `command` (действие: `login`, `save`, `submit`, `accept`, `sign`, `decide`, `reset`).
  - Поддерживаемые варианты ошибок: `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Entity` (с безопасным отображением ошибок полей), `503 Service Unavailable`, `'network'` (сетевая ошибка).
  - Планирование отображается активным бейджем с кнопкой отмены. Неподходящие операции не потребляют запланированный сбой. Повторный клик или уход не вызывают ложных срабатываний.
- **Синтетическая песочница скоринга (`/bank/sandbox`):**
  - Доступна только сотрудникам банка (`bank`).
  - 5 селекторов: базовый профиль (P1–P6), выручка (исходная, заниженная -50%, завышенная +100%), просрочки БКИ (нет, закрытая, текущая просрочка), возраст бизнеса (исходный, молодой <6 мес, зрелый >36 мес) и версия скоринговой политики (`v1.0.0-market`, `v1.1.0-strict`, `v2.0.0-hike`).
  - Расчёт основан на детерминированном реестре из 144 комбинаций и 6 бейзлайнов, заранее вычисленных Python скоринговым ядром и экспортированных в `generated.ts`. В JS отсутствует какой-либо runtime-скоринг или расчет процентов/ставок.
  - Панель отображает хеши входов и результатов, статус маршрутизации, кредитный грейд, баллы, список сработавших факторов и лимитов, сетку офферов (для одобренных вариантов) или отказные причины/стоп-правила.
  - Доступен режим «Сравнить политики»: параллельный просмотр текущей политики и двух альтернативных при гарантированно идентичном `inputHash`.
  - Запуск в песочнице полностью изолирован: не создает заявок, не вносит записей в аудит и не меняет операционные метрики конвейера.
- **Единый сброс (Reset):**
  - Очищает все пользовательские заявки, решения андеррайтера, журнал аудита, результаты песочницы, запланированные сбои и возвращает фабричные 6 примеров в контуре банка.

## Проверка сквозного сценария (фичи 1–14)

25.10.2026: desktop 1280×900 и 1440×900:
1. **Клиентский путь:** Вход `p1` → выбор продукта → сохранение черновика → подача → переход в статус `APPROVED` → выбор предложения → экран подписания → ввод кода `123456` → `SIGNED` → автоматический поллинг до `DISBURSED` («Кредит выдан»).
2. **Контроффер и симулятор:** Вход `p2` → статус `COUNTER_OFFER` → изучение ограничений → симуляция альтернативных параметров (1 210 000 ₽ / 18 мес) → детерминированный ответ скоринга.
3. **Отказы:** Вход `p4` (стоп-факторы БКИ) и `p5` (молодой бизнес, дата повторной подачи).
4. **Контур банка:** Вход `underwriter` → очередь заявок (`/bank/applications`) с фильтрацией/поиском → кредитное досье (`/bank/applications/:id`) с параметрами, трассой факторов и ручным решением андеррайтера → операционные метрики (`/bank/metrics`) с расчетом STP, времени рассмотрения и распределений → песочница скоринга (`/bank/sandbox`) со сравнительным анализом политик.
5. **Сбои и восстановление:** Проверка инжектора ошибок (401 очищает сессию, 409 перечитывает без автоповтора, 422 подсвечивает поля, 503/сеть дают безопасную кнопку повтора).
6. **Сброс:** Кнопка «Сброс демо» с подтверждением восстанавливает исходные 6 примеров и очищает активный сеанс.

Автотесты (312 тестов) проверяют TTL, три неверных попытки, owner/version, восстановление challenge, отмену/гонки запросов, поздний logout, причины P4/P5/P6, ограничения отображения, точную сортировку, ошибки очереди, расчет STP и p95 метрик, а также адресный инжектор сбоев и песочницу скоринга.
